# 한계점 개발 스토리 백로그 구조화

## 배경과 해결할 문제

Impact Lens의 언어 지원 및 분석 한계는 README, INSTALL, 기존 작업 문서와 구현에 분산되어 있다.
현재 알려진 한계는 영향도 순으로 정리할 수 있지만, 각 항목을 독립적으로 계획·구현·검증할 수 있는
개발 스토리와 공통 관리 체계가 없다. 이 때문에 우선순위, 의존성, 완료 조건과 후속 진행 상태를
일관되게 추적하기 어렵다.

별도의 개발 관리 문서 디렉터리를 만들고, 현재 확인된 한계점을 개별 스토리 파일로 분리한다.
각 스토리는 구현을 바로 시작할 수 있을 정도로 문제, 범위, 수용 기준과 검증 방법을 포함한다.

## 범위

- `docs/development-management/`에 개발 관리 문서의 진입점과 운영 규칙을 만든다.
- 한계점의 영향도와 우선순위를 공통 인덱스에서 관리한다.
- 확인된 한계점 13개를 각각 독립된 스토리 문서로 작성한다.
- 각 스토리에 상태, 우선순위, 문제, 사용자 스토리, 범위, 제외 범위, 수용 기준, 검증과 의존성을 기록한다.
- 스토리 사이의 선행 관계와 권장 실행 순서를 문서화한다.
- 기존 개발 가이드에서 새 개발 관리 인덱스를 찾을 수 있도록 연결한다.

## 범위에서 제외할 항목

- 한계점을 해결하는 제품 코드 또는 설정 변경
- GitHub Issue 자동 생성 및 외부 프로젝트 보드 변경
- 미검증 언어를 공식 지원 언어로 선언
- 일정, 담당자 또는 출시 버전의 임의 확정

## 현재 구현 조사 결과

- `README.md`는 정적 Call Hierarchy, 동적 호출, FastAPI DI/decorator, 저장하지 않은 CLI buffer,
  depth/node 제한과 provider 의존성을 설명한다.
- `INSTALL.md`는 기본 TypeScript/JavaScript provider와 사용자 지정 LSP의
  `initializationOptions`/settings 호환성 한계를 설명한다.
- `cli/README.md`는 TypeScript/JavaScript 기본 지원, 사용자 지정 LSP 계약, Personal note 미지원과
  `complete` 의미를 설명한다.
- 실제 TypeScript cross-file LSP 통합 테스트는 있지만 Python/FastAPI Language Server E2E 검증은 없다.
- 기존 개발 문서는 `docs/work/`에 작업별 계획과 로그를 보관하지만, 장기 백로그를 위한 별도 구조는 없다.
- 현재 작업 트리는 clean했고, 병합된 `origin/main`에서 `docs/limitations-story-backlog` 브랜치를 만들었다.

## 단계별 구현 계획

1. 개발 관리 디렉터리의 목적, 상태 모델, 우선순위 기준과 문서 작성 규칙을 정의한다.
2. 한계점 전체 인덱스를 영향도 내림차순으로 작성하고 각 스토리 파일에 연결한다.
3. 13개 한계점을 독립된 스토리로 작성한다.
4. 스토리 간 중복을 검토하고 선행 관계 및 권장 실행 순서를 정리한다.
5. 기존 개발 가이드에 개발 관리 인덱스 링크를 추가한다.
6. 링크, 파일 구조, Markdown 형식과 변경 diff를 검증한다.
7. 작업 로그를 최종 갱신하고 관련 문서만 커밋한다.

## 테스트 및 완료 기준

- `docs/development-management/README.md`에서 모든 스토리로 이동할 수 있다.
- 한계점 13개가 누락이나 중복 없이 개별 파일로 존재한다.
- 모든 스토리가 공통 필수 항목과 검증 가능한 수용 기준을 포함한다.
- 인덱스의 우선순위가 사용자에게 보고한 영향도 내림차순과 일치한다.
- 모든 로컬 Markdown 링크 대상이 존재한다.
- `git diff --check`가 통과한다.
- 구현 범위의 파일과 본 작업 문서를 함께 독립 커밋으로 남긴다.
