# Handover — 2026-09-03 (M2 종료·v0.8.0 발행 완료, M4 stage 2 진행 중)

## 사용자 관점 요약

### 1. 지금까지 어떤 문제가 해결됐고 무엇이 가능해졌는가

**Python·Go·C/C++ 사용자가 provider JSON을 쓰지 않고 "이 함수를 바꾸면 무엇이 영향받는가"에 답을
받습니다.** v0.8.0으로 발행됐고, 발행된 pin으로 실제 동작하는 것까지 두 세션이 독립 확인했습니다.

| 언어 | 설치 필요 | tier |
| --- | --- | --- |
| TypeScript/JavaScript | 아니오 | `bundled` |
| Python (`bundled-pyright`) | **아니오** | `bundled` |
| Go (`gopls`) | 예 | `verified-external` |
| C/C++ (`clangd`) | 예 | `verified-external` |

**그리고 답이 불완전할 때 완전한 척하지 않습니다.** 이게 이 마일스톤의 절반입니다:
- FastAPI `Depends()`·route handler처럼 정적으로 호출자를 볼 수 없는 경우 →
  `provider_null_incoming_calls`("빈 결과가 호출자 없음의 증거가 아니다")
- C/C++에서 `compile_commands.json`이 없으면 cross-file 호출자를 못 봄 → `compile_database_missing`
- `.h`는 C 헤더인지 C++ 헤더인지 모호 → `languageMatch: 'unknown'`(추측해서 한쪽으로 고정하지 않음)

**M2 종료 gate 8개가 전부 닫혔습니다.** 그 과정에서 **shipped된 문서가 최신 clangd에서 틀렸다는 것**과
**clangd 테스트가 우리가 고르지 않은 버전으로 다른 CI job에서 조용히 돌고 있었다는 것**을 찾아 고쳤습니다 —
둘 다 한 번짜리 수동 probe를 반복 검증으로 바꾸는 과정에서만 드러났습니다.

### 2. 아직 무엇이 불가능하거나 오해될 수 있는가

**세 신규 preset은 `verified`가 아니라 `experimental`입니다.** 사용자 검증(실제 사람이 자기 프로젝트로
수행하는 테스트)은 **명세만 작성됐고 실행되지 않았습니다.** M0·M1·M2가 **세 마일스톤 연속으로** 이 검증을
미뤘습니다.

**`verified-external`은 배포 형태이지 검증 등급이 아닙니다.** 이 구분을 PR #67·#68이 세우는 데 두 라운드를
썼고, 릴리스 노트·README·INSTALL 세 곳에 명시돼 있습니다. **다음 사람이 가장 깨뜨리기 쉬운 문장입니다.**

**미검증으로 남긴 것**: clangd 18~21(17=derived 없음, 22/23=있음만 실측), upstream LLVM Releases
바이너리 배너, 그리고 실제 사용자 검증.

**M0가 아직 열려 있습니다** — 9개 gate 중 8개가 닫혔고 남은 하나가 그 사용자 검증 gate입니다.

### 3. 다음 작업은 무엇을 위한 것이며 왜 지금 해야 하는가

**M4(동적 호출·DI·테스트 의미 보완)를 진행 중입니다** — 사용자가 M3(Swift·Kotlin)보다 이쪽을 골랐습니다.

**M2는 "못 본 것을 못 봤다고 말하는" 문제를 풀었습니다. M4는 "못 본 것을 추론해서 보여주는" 문제입니다.**
FastAPI 사용자는 지금 빈 결과에 경고만 받습니다 — 정직하지만 **호출자가 누구인지는 여전히 직접 찾아야
합니다.** M4가 그 호출자를 후보로 보여줍니다.

**위험이 M2와 정반대입니다.** M2는 빈 결과가 증명된 0으로 읽히는 걸 막았고, **M4는 추측한 edge가 확정된
edge로 읽히는 걸** 막아야 합니다. 그래서 stage 1을 **코드 없는 설계 게이트**로 두고 계약부터 확정했습니다.

## M4 계약 — 다음 사람이 어기면 안 되는 것

`docs/work/task-m4-stage1-evidence-contract.md`가 전문입니다. 요약:

1. **추론 edge는 `data.augmentedEdges`로 나가고 기존 `edges`는 필드 하나, 값 하나 안 바뀝니다.**
   섞으면 additive가 아닙니다 — 옛 소비자에게 **추측이 확정으로 조용히 승격**됩니다.
2. **`data.nodes`에 항목을 추가하지 않습니다.** endpoint는 (a) **그 실행의 `nodes`에 실재하는** id 또는
   (b) self-contained. **확인 불가면 (b)** (traversal이 잘리면 (a)가 dangling이 됩니다).
3. **추론 탐색은 별도 budget을 씁니다.** static과 공유하면 `complete`/`truncated`/`traversalStatus` 등
   **다섯 필드가 augmentation 때문에 뒤집힙니다.**
4. **M2 신호는 안 사라집니다.** adapter가 caller를 찾아도 `provider_null_incoming_calls`는 그대로입니다 —
   provider는 **여전히 못 봤고** 우리가 추론했을 뿐, 그 둘은 다른 사실입니다.
5. **`resolution`은 `single`/`multiple` 둘뿐.** 확정 불가면 edge를 만들지 말고 limitation만 냅니다.
6. **`confirmed`를 `augmentedEdges` 안에서 쓰지 않습니다** — `edges`가 이미 뜻하는 단어입니다.
7. **kill switch는 양방향 검증**: 끄면 M4 이전과 동일, **켠 상태에서도** `nodes`/`edges`/위 다섯 필드 불변.

**M1이 이미 배관을 깔아 뒀습니다** — `static-plus-inference`, `inferred_edges_included` 등이 있고
**producer가 0건**입니다. `augmentedEdges`가 채워지면 기존 코드가 자동으로 `coverage.semantic`을 냅니다.

## 작업 방식 메모

**3세션 분리**(계획/구현/검토)가 이 세션 내내 유지됐고, **검토 lane이 merge 전에 실제 결함을 반복해서
잡았습니다.** 특히:

- 계획 세션(이 세션)의 **잘못된 지시가 3회** 있었고 전부 구현 전 또는 merge 전에 잡혔습니다.
- **되돌리기 어려운 외부 행위(tag/Release 발행)는 승인을 가진 세션이 직접 수행**했습니다. 준비(artifact
  생성)는 구현 세션이, 발행은 계획 세션이.
- **반복된 실패 형태 셋**: ① 측정한 사실에 검증 안 된 한 걸음을 이어 붙이며 이음매를 표시 안 함,
  ② 고친 쪽만 확인하고 반대 방향을 안 봄, ③ `cd` 후 상대 경로 검색이 실재하는 다른 파일을 조용히 뒤짐.
- **"찾지 못했다"와 "없다"는 다른 진술**이라는 원칙이 여러 번 결정적이었습니다.
