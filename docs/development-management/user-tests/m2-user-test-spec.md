# M2 사용자 테스트 명세 — Python·Go·C/C++ 검증된 언어 지원

- 대상 마일스톤: [M2 — Python·Go·C/C++ verified support](../milestones/m2-p1-language-support.md) 4단계
- 작성 기준 코드 상태: `main`에 merge된 M2 lane 전체(Python `bundled-pyright`, Go `gopls`,
  C/C++ `clangd`). **발행 버전이 아니라 merge된 코드 기준으로 쓴다** — M1 명세가 발행 버전과 작성 기준을
  혼동해 사후 정정이 필요했던 전례를 반복하지 않는다.
- 상태: 작성 완료, **검토 대기**. **아직 실행하지 않았다.**
- 작성 규칙: [마일스톤별 사용자 테스트 명세 계획](../milestones/user-validation-planning.md)
- 근거: [IL-LIM-004](../stories/il-lim-004-first-class-language-presets.md),
  [IL-LIM-006](../stories/il-lim-006-python-provider.md),
  [IL-LIM-014](../stories/il-lim-014-c-cpp-clangd-support.md),
  [IL-LIM-009 완전성 의미론](../stories/il-lim-009-completeness-semantics.md)

이 문서는 명세일 뿐이며, 존재만으로 사용자 검증을 통과한 것으로 표시하지 않는다. 실행은 별도 승인,
참여자 모집과 환경 준비 후에 수행한다.

설치·초기화·runner 우선순위는 M0 이후 바뀌지 않았으므로 [M0 테스트 환경 구성과 초기화
가이드](m0-environment-setup.md)를 그대로 따른다. M2에서만 필요한 준비는 §5에서 그 위에 더한다.

## 1. 검증 목적

M2의 종료 gate는 세 언어에서 **사용자가 raw provider JSON을 쓰지 않고** 분석을 시작하고, 준비가
안 된 상태를 이해하며, 정적 분석이 못 보는 호출을 과신하지 않는지를 본다. 자동 검사는 이미 기계 쪽
절반을 증명했다 — 3-OS CI가 세 provider 전부에서 실제 Call Hierarchy 왕복을 돌고, `compile_database_missing`과
`provider_null_incoming_calls`가 실제 응답에 실린다는 것도 real E2E로 증명됐다. **이 테스트는 나머지
절반, 사람이 그 값을 실제로 그렇게 읽는지를 본다.**

1. **세 언어 각각에서 Auto로 시작한다.** provider command를 모른 채 자기 프로젝트에서 함수 영향을
   확인할 수 있는가. (§6 T1)
2. **언어마다 다른 준비 요구를 이해한다.** Python은 아무것도 설치할 필요가 없고, Go와 C/C++는 사용자가
   provider를 직접 설치해야 한다. **이 차이가 도구 고장이 아니라 설계임을 이해하는가.** (§6 T2)
3. **준비 실패의 두 가지 다른 모양을 구분한다.** Go는 `go.mod`가 없으면 **막고**, C/C++는
   `compile_commands.json`이 없어도 **답을 주되 경고한다.** 후자에서 빈 결과를 "호출자 없음"으로
   읽지 않는가. **이 문서에서 가장 값진 과업이다.** (§6 T3)
4. **언어별 정적 한계를 과신하지 않는다.** Python DI/decorator, C function pointer, C++ virtual
   dispatch가 결과에서 빠지는데도 "안 쓰인다"고 결론짓지 않는가. (§6 T4)

## 2. 이번 테스트로 판단하지 않을 항목

정적 Call Hierarchy의 절대 정확도, 대규모 workspace 성능(M5), Note 사용성(M6), graph 시각 디자인,
성공률·지연 시간의 합격 수치(§10에서 baseline만 잰다)는 판단하지 않는다. M1이 검증한 계층(Auto 선택
기계, doctor 복구, `complete` 의미론)은 M2에서 바뀌지 않았으므로 다시 판단하지 않는다.

**언어 간 비교도 하지 않는다.** 이 테스트는 "어느 언어가 더 잘 되는가"를 재지 않는다. 마일스톤 5단계가
**preset별 독립 승격 결정**을 요구하므로, 한 언어의 결과가 다른 언어의 판정에 들어가지 않는다.

**pyright vs basedpyright, clangd 배포판 간 차이도 판단하지 않는다.** 각 preset이 고정한 하나만 본다.

## 3. 참여자

언어별로 **독립 모집**한다. 한 사람이 두 언어를 수행하지 않는다 — 첫 언어에서 배운 것이 두 번째 언어의
T3·T4 판단을 오염시킨다(이 과업들이 재는 것이 바로 "처음 보고 어떻게 읽는가"이다).

- 언어당 pilot 2명 + 본 라운드 4명. **세 언어 독립이므로 총 6 + 12명.**
- 자격: 해당 언어로 **자기 코드베이스를 하나 이상 유지**하고 있을 것. 합성 프로젝트를 주지 않는다 —
  준비 상태(venv/go.mod/compile database)가 실제로 어떤지가 이 테스트의 대상이기 때문이다.
- 제외: 이 저장소에 기여한 적 있는 사람, Impact Lens의 provider 계층을 아는 사람.

## 4. 환경 matrix

| 언어 | provider | 사용자가 설치해야 하는가 | OS |
| --- | --- | --- | --- |
| Python | `bundled-pyright` | **아니오**(CLI가 번들) | macOS / Linux / Windows |
| Go | `gopls` | 예 | macOS / Linux / Windows |
| C/C++ | `clangd` | 예 | macOS / Linux / Windows |

각 언어 × 3 OS를 최소 1회씩 덮는다. Host는 M1과 동일(CLI 직접, Extension, Plugin runner) — **단 T3·T4는
Plugin runner에서 최소 1회 수행한다.** 에이전트 요약이 한계를 옮기는지가 그 조합에서만 관측된다.

## 5. 시작 상태와 사전조건

M0 가이드에 더해, **참여자 프로젝트의 준비 상태를 사전에 고치지 않는다.** 진행자는 다음을 기록만 한다:

- Python: venv 유무, 활성화 여부, third-party import 사용 여부.
- Go: `go.mod` 유무, module 모드인지.
- C/C++: `compile_commands.json` 유무와 경로, 빌드 시스템(CMake/Make/기타).

**이 값들이 T2·T3의 시작 조건이고, 정리해 버리면 이 테스트가 재려는 것이 사라진다.** 참여자 프로젝트가
이미 완벽히 준비돼 있다면 T3는 §6의 절차로 **의도적으로 준비를 제거한 사본**에서 수행한다(원본은
건드리지 않는다).

## 6. 과업

각 과업은 **자유 서술 단계 → 확인 단계** 순서다. 진행자는 자유 서술 단계에서 어떤 힌트도 주지 않는다.

**T1 — Auto로 첫 분석.** 자기 프로젝트에서 함수를 하나 고르고 "이 함수를 바꾸면 무엇이 영향받는가"를
확인한다. provider 설정 파일을 쓰지 않는다. Python 참여자는 아무것도 설치하지 않고, Go·C/C++ 참여자는
도구가 안내하는 대로 provider를 설치한다.

**T2 — 설치 안내만으로 복구.** (Go·C/C++ 전용) provider가 PATH에 없는 상태에서 시작한다. 진행자가
설치 방법을 알려주지 않고, **도구 출력만으로** 복구할 수 있는지 본다. Python 참여자는 이 과업 대신
"왜 나는 아무것도 설치하지 않았는가"를 설명하게 한다 — 번들 tier를 이해하는지 본다.

**T3 — 준비 안 된 상태의 두 모양.** 언어별로 다르다.
- **Go**: `go.mod`가 없는 디렉터리에서 분석을 시도한다. 도구가 **막는다.** 참여자가 이것을 도구 고장이
  아니라 "module 정의가 필요하다"로 읽는가.
- **C/C++**: `compile_commands.json`이 없는 상태에서, **다른 파일에 호출자가 있는 함수**를 조회한다.
  도구는 **빈 결과 + `compile_database_missing` 경고**를 준다. 참여자에게 **"이 결과를 보고 이 함수에
  대해 무엇을 알게 됐습니까?"**를 자유 서술로 답하게 한다 — **"호출자가 있습니까?"라고 묻지 않는다.**
  그렇게 물으면 caller 존재라는 틀 자체를 진행자가 심는다. **참여자가 묻지 않았는데도 "아무도 안
  부른다"에 스스로 도달하는지**가 관측 대상이다. 자유 서술이 끝난 뒤에 실제로 호출자가 있음을 보여준다.
- **Python**: venv 없이 third-party import가 있는 파일에서 분석한다. 관측만 한다(현재 이 경우의 동작은
  준비 실패로 분류되지 않는다 — 이 과업은 그 사실이 사용자에게 혼란인지를 재는 것이다).

**T4 — 정적 한계.** 언어별로 정적 분석이 못 보는 호출 경로가 있는 함수를 조회하게 한다.
- **Python**: DI/decorator로만 호출되는 함수(FastAPI `Depends()`, Flask route 등). 응답에
  `provider_null_incoming_calls`가 실릴 수 있다.
- **C**: function pointer로만 호출되는 함수.
- **C++**: virtual dispatch로 파생 클래스에서만 호출되는 메서드.

**T4 진행 절차 — 유도 금지가 이 과업의 핵심이다. M1 §6의 규칙을 그대로 따른다.**

참여자에게 묻는 문장은 **"이 결과를 보고, 이 함수에 대해 다음에 무엇을 하시겠습니까?"** 하나다.
선택지를 주지 않는다.

**진행자가 먼저 꺼내지 않는 단어**: `지워`, `삭제`, `안 쓰인`, `안전`, `완전`, `한계`, `caveat`.
**"이 함수를 지워도 됩니까?" / "이 결과가 안전해 보이나요?" 같은 질문은 답을 심는 질문이므로 금지한다.**
두 형태 모두 (a) 특정 행동을 진행자가 먼저 이름 붙이고 (b) yes/no 허가형으로 판단을 유도한다. M1이
이 패턴을 명시적으로 금지했고(§6, §14), 이 명세의 첫 초안이 정확히 그 금지를 어겼다가 검토에서
정정됐다 — 같은 실수가 다시 들어가지 않도록 여기 남긴다.

참여자가 **스스로** 삭제·미사용 판단에 도달하는지, 그리고 그때 정적 범위의 한계를 **스스로** 언급하는지가
관측 대상이다. §8의 지표는 질문 문구가 아니라 **참여자 발화에서 사후 판정**한다.

## 7. 과업별 기대 결과와 중단 조건

- T1이 provider 설정 없이 성공하지 못하면 그 언어의 나머지 과업을 진행하지 않고 중단한다.
- **T3·T4의 자유 서술 단계에서 진행자가 힌트를 주면 그 세션은 무효**다. 무효 세션 비율은 §10의 판정
  항목이다 — 절차 자체의 결함으로 본다.
- 참여자 프로젝트를 도구가 자동으로 build·install·수정하면 **즉시 중단하고 결함으로 보고**한다.

## 8. 관측 지표

- T1: time-to-first-success, provider 설정 파일을 열어본 횟수(0이어야 한다).
- T2: 복구까지의 시도 수, 참여자가 참조한 출력 필드.
- T3: **참여자가 자유 서술에서 "호출자가 없다"고 단정한 비율**(C/C++), 도구 고장으로 결론지은 비율(Go).
- T4: **함수를 지워도 된다고 답한 참여자 중 정적 범위 한계를 스스로 언급하지 않은 비율.**
- 전 과업: 자동 build·install·수정이 일어난 횟수(**0이어야 하는 안전 불변식**).
- Plugin runner 조합에서는 **에이전트 요약 원문을 매번 기록**한다(§12).

## 9. 사후 질문

**이 절의 질문은 해당 과업의 자유 서술이 완전히 끝난 뒤에만 쓴다.** §6이 금지한 단어(`완전`, `안전`,
`한계` 등)를 여기서는 쓰는데, 그때는 이미 관측할 발화가 기록된 뒤이므로 유도가 성립하지 않는다.
**자유 서술 중에 이 질문을 앞당겨 쓰면 그 세션은 무효다**(§7).

- "이 결과가 완전하다고 생각했습니까? 왜 그렇게 생각했습니까?"
- (C/C++) "경고 문구를 읽었습니까? 무슨 뜻으로 이해했습니까?"
- (Go vs C/C++ 참여자 각각) "도구가 막았을 때 / 답을 줬을 때 어느 쪽이 이해하기 쉬웠습니까?"
- "이 도구가 못 보는 호출이 있다면 어떤 것일 것 같습니까?"

## 10. 통과·보류 기준

수치 기준은 지금 추측하지 않는다. 언어별 pilot 2명의 결과로 baseline을 만든 뒤 본 라운드 기준을
확정한다 — M0·M1과 같은 규칙이다. **baseline도 언어별로 따로 만든다.**

**정성 통과 기준** (본 라운드 확정 전에도 적용):

- 모든 OS × Host 조합에서 T1이 provider 설정 없이 성공한다.
- T2에서 Go·C/C++ 참여자 과반이 진행자의 직접 답변 없이 provider를 설치해 복구한다.
- T3(Go)에서 아무도 `go.mod` 요구를 도구 고장으로 결론짓지 않는다.
- **T3(C/C++)에서 자유 서술 단계에 "호출자가 없다"고 단정한 참여자 전원이 경고 문구를 언급하지 않으면
  (0명 언급) 그 자체로 C/C++ preset의 verified 승격을 보류한다.** baseline 없이도 지금 바로 적용되는
  유일한 T3 기준이다.
- **T4에서 함수를 지워도 된다고 답한 참여자 전원이 정적 범위의 한계를 스스로 언급하지 않으면(0명 언급)
  그 언어의 승격을 보류한다.** 언어별로 독립 적용한다.
- 어떤 과업에서도 도구가 참여자 프로젝트를 자동으로 build·install·수정하지 않는다.
- 진행자 유도로 무효 처리된 세션 비율이 0이다.

**보류 기준**: 위 항목 중 하나라도 미달하면 **그 언어의 preset만** verified로 승격하지 않는다. 다른
언어의 판정에 영향을 주지 않는다(마일스톤 5단계 요구). T3·T4가 미달하면 코드가 아니라 **문구**를 먼저
의심한다 — `compile_database_missing`의 message/action, `provider_null_incoming_calls`의 문구,
`docs.limitations` 항목, 그리고 Plugin의 응답 정책이 실제 사람에게 통하는지가 이 과업이 재는 것이다.

**승격 등급**: 통과하면 `verified`, T1은 통과하나 T3/T4가 미달하면 `experimental`, T1이 실패하면
`unsupported`. **등급은 언어별로 따로 기록하고 평균 내지 않는다.**

## 11. Privacy와 동의

- 참여자 동의 없이는 어떤 기록도 수집하지 않는다. 동의 범위를 과업 시작 전에 문서로 확인한다.
- **참여자는 자기 실제 코드베이스를 쓴다.** 화면 기록·출력 수집 전에 사내 코드 공개 가능 여부를 확인하고,
  불가하면 함수명·경로를 가린 요약만 수집한다.
- `compile_commands.json`에는 사용자 환경 경로와 define이 들어 있다. **doctor 출력을 수집할 때 그 값이
  포함되지 않는지 진행자가 확인한다**(도구는 이미 redaction하지만, 수집 절차도 같은 가정을 하지 않는다).

## 12. 증거 형식

- 과업별 화면 기록 또는 터미널 로그(동의 범위 내).
- **Plugin runner 조합에서는 에이전트 요약 원문 전체.** 요약은 매번 새로 생성되므로 참여자마다 문구가
  다를 수 있다 — 두 참여자가 다른 결론에 도달했을 때 **참여자 편차로 단정하기 전에 원문을 나란히 놓고
  실제로 다른 문구를 봤는지부터 확인한다**(M1 명세와 같은 규칙).
- 응답 JSON의 `limitationDetails` 전문. 참여자가 무엇을 볼 수 있었는지를 사후에 재구성하려면 필요하다.

## 13. 실패 처리와 재시험

- 도구 결함이 확인되면 수정 후 **그 언어만** 재시험한다.
- 절차 결함(유도, 준비 상태 오염)이 확인되면 §6을 고치고 해당 세션을 폐기한다.
- **한 언어의 재시험이 다른 언어의 일정을 막지 않는다.**

## 14. 검토 체크리스트

- [ ] 세 언어의 과업이 실제로 독립적인가(한 언어 결과가 다른 언어 판정에 안 들어가는가).
- [ ] T3의 Go/C/C++ 비대칭(막음 vs 경고)이 과업 설계에 정확히 반영됐는가.
- [ ] T4의 언어별 한계 예시가 실제로 그 preset의 `docs.limitations`에 적힌 것과 일치하는가.
- [ ] **T4가 자유 서술을 먼저 요구하고, "지워도 됩니까" / "안전해 보이나요" 형태의 유도 질문이 어디에도
  없는가.** (M1 §14와 같은 항목 — 이 명세의 첫 초안이 여기서 걸렸다.)
- [ ] **T3(C/C++)가 "호출자가 있습니까"로 묻지 않고 개방형으로 묻는가.**
- [ ] §6의 금지 단어 목록이 §8·§9의 문구와 충돌하지 않는가(사후 질문은 자유 서술이 끝난 뒤에만 쓴다).
- [ ] 참여자 프로젝트의 준비 상태를 진행자가 고치지 않는가.
- [ ] Privacy 항목이 실제 코드베이스 사용과 compile database 경로 유출을 둘 다 다루는가.
- [ ] 승격 등급이 언어별로 독립 기록되는가.
